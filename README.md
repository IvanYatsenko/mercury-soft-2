# Mercury

Учебный проект управления печью оплавления. Развиваем небольшими шагами:
задача → самостоятельная реализация → ревью → проверка.

## Что есть сейчас

- `apps/web` — браузерный клиент: React, TypeScript, MUI, Vite.
- `apps/panel` — Electron + TypeScript для встроенного экрана печи; использует тот же React-интерфейс.
- `apps/server` — Node.js + TypeScript, REST API и подключение платы по USB/Serial через ITMP.
- `packages/shared` — общие типы температурных профилей для сервера, браузера и панели.
- `packages/shared/ovens` — JSON-конфигурации Меркурий-300 и Меркурий-400;
  происхождение данных и расхождения описаны в `docs/oven-configurations.md`.
- MobX установлен; первый store добавим, когда появится состояние приложения.
- Строгая проверка TypeScript, Prettier, единый lockfile.

Сервер умеет проверять состояние платы, отправлять флаг готовности и выключать плату.
В настройках доступна краткая проверка отдельных элементов печи; автоматическое
управление нагревом в проекте пока не реализовано.

## Запуск

Нужны Node.js 24 LTS и pnpm 11.25.0. Если pnpm отсутствует:

```sh
npm install --global pnpm@11.25.0
```

Из корня проекта:

```sh
pnpm install --frozen-lockfile
pnpm dev
```

`pnpm dev` запускает сервер, Vite и окно Electron. Vite ждёт ответа API, а Electron —
готовности обоих серверов (до 60 секунд). Если окно Electron закроется или не запустится, сервер и браузерный
интерфейс продолжат работать. Ctrl+C останавливает группу процессов.

Открыть в браузере http://127.0.0.1:5173. API: http://127.0.0.1:3001/api/health.
Vite перенаправляет `/api` на сервер. Оба процесса пока слушают только localhost.
`pnpm dev:web` запускает только сервер и браузерный интерфейс — для клиента ПК.
React обновляется автоматически; после изменений основного процесса Electron перезапусти `pnpm dev`.

В аппаратном режиме сервер открывает последовательный порт, читает `get` и `stat`,
затем при состоянии `STARTING` отправляет флаг готовности `stat [2]`.
Проверка по адресу http://127.0.0.1:3001/api/controller/check возвращает
числовое состояние платы, связь и показания. Браузер повторяет запрос шаблонов,
если API ещё запускается.

## Настройки

В корне проекта есть файл `.env`. Измени его перед запуском приложения:

```dotenv
MERCURY_CONTROLLER_MODE=simulation
MERCURY_SERIAL_PORT=auto
MERCURY_API_PORT=3001
MERCURY_WEB_PORT=5173
```

`simulation` запускает виртуальную плату. Для реальной платы укажи `hardware`.
`auto` выбирает `COM4` в Windows и `/dev/ttyUSB0` в Linux/macOS (как старое ПО
при разработке). Если плата на другом порту, впиши его явно; на Raspberry Pi
это может быть `/dev/ttyS0`. `MERCURY_API_PORT` меняет порт сервера, `MERCURY_WEB_PORT` —
порт Vite. Vite и Electron читают эти же значения. После изменения `.env`
перезапусти `pnpm dev`. `.env` не попадает в Git; `.env.example` содержит пример.

При первом открытии интерфейс предложит выбрать модель печи и вариант платы
220/380 В. Выбор сохраняется в корневом `config.json` и восстанавливается после
перезапуска. Позже его можно изменить на странице «Настройки печи». Этот файл
также не попадает в Git. Данные моделей лежат отдельно в
`packages/shared/ovens/300.json` и `400.json`.

В аппаратном режиме сервер регулярно читает `get` и `stat`. Если плата сообщает
`STARTING`, сервер отправляет `stat [2]` и проверяет, что состояние стало
`WORKING`. Состояние связи видно по цветному индикатору в верхней панели.

Значок Wi-Fi в верхней панели открывает список сетей. На Raspberry Pi для поиска,
подключения и отключения используется NetworkManager (`nmcli`). Пароль вводится
экранной клавиатурой. На Windows управление сетью недоступно: сервер не меняет
подключение компьютера разработчика. API: `GET /api/wifi/status`,
`GET /api/wifi/networks`, `POST /api/wifi/connect`, `POST /api/wifi/disconnect`,
`POST /api/wifi/radio`.

## Запуск собранной версии

```sh
pnpm build
pnpm start
```

Сервер отдаёт собранный React-интерфейс и API на http://127.0.0.1:3001.
Electron открывает этот адрес; его можно открыть и в браузере.
Это локальный запуск сборки, не установщик и не готовое развёртывание на Raspberry Pi.
Для него позже отдельно настроим автозапуск сервиса, kiosk-режим и сборку под ARM.
Интерфейс Electron работает с изоляцией контекста, sandbox и без доступа к Node.js.
Preload/IPC пока не нужны: клиент обращается к серверу по HTTP.

## Проверки

```sh
pnpm typecheck
pnpm format:check
pnpm build
```

`pnpm check` выполняет все три проверки. `pnpm format` форматирует файлы.
Сборка создаёт `dist` внутри каждого приложения; эти файлы не коммитятся.
`pnpm --filter @mercury/server start` запускает собранный API.
`pnpm --filter @mercury/web preview` показывает собранный UI, но не проксирует API:
для совместного запуска при разработке используй `pnpm dev`.

## Направление развития

Node.js-сервис на Raspberry Pi будет работать с контрольной платой и хранить данные.
ПК подключается по IP через браузер: Electron на ПК не нужен.
Локальный экран печи использует Electron, мобильный клиент позже получит React Native.
REST API обслуживает запросы и команды; события состояния добавим отдельно.
Базу данных и мобильное приложение подключим на соответствующих учебных этапах.

## Ближайшее задание

Описать точку температурного профиля и профиль на TypeScript, затем написать
проверки чисел и порядка времени. Готовой реализации в шаблоне нет.

Старая версия используется только как справочный материал по оборудованию;
перенос её архитектуры не планируется.

## Разработка без платы

При `MERCURY_CONTROLLER_MODE=simulation` сервер использует виртуальную плату.
Кнопка выключения в интерфейсе меняет её состояние. Текущие флаги,
температуры и выходы можно посмотреть по адресу
http://127.0.0.1:3001/api/controller/virtual-board (если изменил порт API,
используй его новое значение). Описание поведения платы и копия исходников
прошивки находятся в `docs/firmware-source`.
