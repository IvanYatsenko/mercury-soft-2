# Совместимость с программой мониторинга

Сервер публикует `GET http://<IP-печи>:3457/status` в формате старого приложения. Привязка сети берётся из `MERCURY_API_HOST`; порт задаётся `MERCURY_MONITORING_PORT` (по умолчанию 3457). `MERCURY_MONITORING_ENABLED=false` отключает отдельный слушатель. Этот же ответ доступен на основном HTTP-порту по `/status`.

Ответ содержит `profile`, `heatIndicators`, `status`, `state`, `progress`, `errorStore`, `version`. Программа MercuryFurnace из запроса читает `status`, `state.second`, `state.timeHorizon`, `state.profileName`, пять числовых счётчиков ошибок и версию — эти поля сохранены.

- `status`: `busy` для подготовки, выполнения, паузы и охлаждения активного профиля; `finish` для завершённого/остановленного/ошибочного запуска до «Готово»; `idle` после «Готово», при ожидании и фоновом поддержании.
- `state.second`: текущая секунда текущего цикла, включая старт с найденной точки профиля. `timeHorizon`: оставшиеся секунды текущего цикла, а не сумма всех повторов.
- `coreTemp`: температура процессора Raspberry строкой вида `51.12°C`; пустая строка при отсутствии измерения.
- `temperature`: внутренний датчик контрольной платы, как `t7` в старом `ovenStore.js`. Это не термопара камеры или изделия.
- `convFreq.Hz`: измеренная частота, `rel`: отношение к эталону.
- `heatIndicators`: мгновенные состояния выходов в виде 0/100, а не измеренная электрическая мощность.
- `errorStore`: счётчики эпизодов с запуска текущего профиля; обнуляются событием начала нового запуска. Длительная ошибка не считается заново при каждом GET. Учитываются отклонение профиля, обороты, дверь при выполнении, температурные/сенсорные ошибки и потеря ITMP-связи.
- `progress`: пустой массив. История не накапливается в RAM ради мониторинга; предоставленный клиент это поле не использует. Данные запусков остаются только на исправном USB.

Ответ строится из уже полученных измерений и готового состояния процесса. GET не читает UART, конфигурацию или USB, не запускает нагрев и не меняет настройки. При отсутствии актуальных данных платы (включая устаревание более 6,5 секунды) возвращается HTTP 503; это попадает в `handleError` программы мониторинга. Ошибки самого профиля при живой связи доступны в нормальном ответе и счётчиках.

POST `/status` возвращает 405, команды `/api/...` — 404. Ошибка открытия дополнительного порта журналируется без остановки управления печью. Версия берётся из корневого `package.json`.

## Запуск и остановка на порту 3457

`POST /profile/start` принимает объект профиля JSON с `Content-Type: application/json` и заголовком `X-Mercury-Pin: <PIN>`. Подходит отправка файла через `curl --data-binary @profile.json`. Допустима также оболочка `{ "pin": "<PIN>", "profile": { ... }, "acceptWarnings": true }`.

`POST /profile/stop` с тем же заголовком останавливает текущий процесс. PIN проверяется заново для каждой команды; операторский PIN не подходит. GET `/status` остаётся открытым.

Профиль передаётся общему исполнителю без добавления в библиотеку профилей. `X-Mercury-Accept-Warnings: true` включает проверку совместимости, `false` пропускает её. Без заголовка проверка включена. При включённой проверке предупреждения подтверждаются полем `acceptWarnings: true` в оболочке. Корректность JSON и обязательные ограничения исполнителя проверяются всегда. Некорректный JSON/профиль — 400, неподходящий PIN — 423, конфликт состояния или неподтверждённые предупреждения — 409, завершение работы/обновление — 503. Максимальный размер JSON — 256 КБ.
