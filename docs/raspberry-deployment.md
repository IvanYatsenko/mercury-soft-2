# Raspberry Pi

Испытательная установка: Debian 12 ARM64, пользователь `pi`, Xorg `DISPLAY=:0`,
резистивный дисплей 480×320. Контроллер подключён через `/dev/serial0`.

Исходники и сборка находятся в `/home/pi/mercury-v3`. Зависимости устанавливаются
на Raspberry Pi; Windows `node_modules` не переносится.

`scripts/raspberry-install.sh` устанавливает проверенную по SHA-256 официальную
сборку Node.js 24.21.0 ARM64, pnpm 11.25.0 и собирает пакеты последовательно.
Первый запуск использует виртуальную плату. Параметры в `.env`:

```dotenv
MERCURY_CONTROLLER_MODE=simulation
MERCURY_SERIAL_PORT=/dev/serial0
MERCURY_API_PORT=3001
MERCURY_WEB_PORT=5173
MERCURY_PANEL_FULLSCREEN=true
MERCURY_PANEL_SOFTWARE_RENDERING=true
```

Для реального контроллера используется `MERCURY_CONTROLLER_MODE=hardware`.
Одновременно запускать старое и новое ПО с реальной платой нельзя.

Для работы с ПК в той же подсети задайте на Raspberry
`MERCURY_API_HOST=0.0.0.0` и откройте в браузере `http://<IP Raspberry>:3001/`.
На установках 21 октября 2026: М400/230 В — `http://10.10.1.167:3001/`,
М300/380 В — `http://10.10.1.88:3001/`. Привязку модели всегда проверяйте
через настройки устройства: IP не определяет модель. Сервер отдаёт интерфейс
и API с одного адреса; браузер ПК не подключается к UART. Выполнение профиля
остаётся на Raspberry при закрытии браузера или потере Wi-Fi.
Для широкого экрана предусмотрена увеличенная рабочая область; при наличии
мыши поля используют обычную клавиатуру. На дисплее 480×320 сохраняются
сенсорная клавиатура и кнопки прокрутки. Нагревательные настройки при включении
сетевого доступа менять не требуется.

Установка из универсального архива использует программу
`/opt/mercury-v2/program` и пользовательскую службу `mercury-v2`.
Конфигурация и профили находятся в `/home/pi/.config/mercury-v3`,
история и технический журнал — только на USB `/media/flash`.

Для прежней установки из исходников пользовательская служба
`deploy/raspberry/mercury-v3.service` запускает сервер и
Electron вместе через `scripts/raspberry-start.sh`. Настройка предназначена для
установки в указанную папку под пользователем `pi`.

```sh
systemctl --user status mercury-v3
journalctl --user -u mercury-v3 -n 80 --no-pager
curl http://127.0.0.1:3001/api/health
```

Старое ПО остаётся в `/opt/mercury-v2`. Для возврата:

```sh
systemctl --user disable --now mercury-v3
systemctl --user enable --now mercury-v2
```

Для нового ПО:

```sh
systemctl --user disable --now mercury-v2
systemctl --user enable --now mercury-v3
```

Пользовательские профили старого ПО v2 автоматически не импортируются.
Прототип v3 хранит профили и историю в SQLite и выполняет профиль на сервере.
Текущее состояние и ограничения описаны в `docs/prototype-plan.md`.

Проверка установки 2 октября 2026: новая служба включена в автозапуск,
используется режим `hardware`, плата отвечает через `/dev/serial0` и находится
в состоянии `WORKING`. Проверены реальные температуры, работа конвекционного
вентилятора и полноэкранный интерфейс 480×320 по снимку дисплея. Нагреватели
не включались. Пользователь подтвердил успешный запуск после перезапуска печи.
Физический сенсор ещё нужно проверить.

Охлаждение самого Raspberry Pi управляется сервером отдельно от вентиляторов
печи. Модуль активируется только на Linux с моделью `Raspberry Pi` в
`/proc/device-tree/model`. Температура CPU читается каждые 5 секунд: выше 60 °C
вентилятор включается, ниже 50 °C выключается. Между порогами сохраняется
состояние; при первом запуске в этом диапазоне охлаждение включено.
При ошибке чтения температуры сервер также включает охлаждение.

Используется GPIO4 и `gpioset` из libgpiod 2.x (на испытательной Pi — 2.1.2).
Процесс `gpioset` удерживает линию всё время работы, поскольку после его
завершения состояние GPIO не гарантируется. Пользователь сервера должен иметь
доступ к GPIO (на испытательной Pi пользователь `pi` входит в группу `gpio`).
Изменения состояния и ошибки доступны в журнале `mercury-v3`.

При физическом выключении печи сервер обнаруживает флаг `SHUTDOWN` (бит 32)
от платы. Только на реальной Raspberry Pi он завершает запись `config.json`,
подтверждает плате задержку отключения 30 секунд и запускает отдельную системную
службу через `sudo -n systemd-run`. Сценарий `scripts/raspberry-poweroff.sh`
останавливает пользовательскую службу приложения, выполняет `sync` и
запускает отдельный помощник `shutdownBoard.js`, который отправляет плате
`poweroff [5]` через освобождённый UART. ОС Raspberry Pi не выключается:
питание снимает плата печи. Предварительная команда `poweroff [30]` только
увеличивает время ожидания платы на завершение приложения. Нужны systemd и права sudo без пароля; на испытательной
Pi они доступны. Если запуск выключения не удался, ошибка записывается в журнал,
попытка повторяется. При выключении плата не инициализируется заново.

Профили и выбор профиля сохраняются в SQLite на сервере. Прежние профили
из хранилища интерфейса v3 переносятся однократно; исходная копия в браузере
сохраняется. При завершении сервер останавливает нагрев и сбрасывает журнал
SQLite на диск. Незавершённый черновик редактора не сохраняется. Настройки оборудования и подтверждённая
частота конвекции записываются сервером в `config.json`.

Проверка сценария без отключения питания:
`sh scripts/raspberry-poweroff.sh --dry-run`. Полное физическое выключение
после внедрения этой логики требует отдельной проверки на печи.
