Комментарии перед методами описывают назначение и важные ограничения. Детали типов остаются в TypeScript. При изменении поведения обновляйте соответствующий комментарий и документацию вместе с реализацией.

Нумерация моделей уточнена: М300/М400 — старые платы только 220 В;
М301/М401 — новые платы 220/380 В. Внутренние JSON-ключи размерных серий
сохранены. Правила отображения и совместимости данных описаны в
[определении моделей](oven-model-identification.md).

## Поток управления

1. Клиент отправляет действие с собственным идентификатором доступа. Сервер проверяет PIN-уровень, завершение питания, состояние платы и конфигурацию.
2. Профиль проходит общую валидацию. Внешний импорт и передача не должны автоматически запускать нагрев.
3. `ProfileRunner` строит план и на каждом шаге выбирает заданную температуру. Измерение берётся из указанной профилем термопары.
4. Регулятор и прогноз формируют запрос выходов. Защита ламп и транспорт применяют разрешённые фактические значения.
5. Телеметрия, живые события и USB-история обслуживают читателей независимо от выполнения процесса.

Не отправляйте команды платы из нового маршрута в обход общей очереди. Не создавайте второй исполнитель нагрева для калибровки или поддержания. Для реального оборудования перед испытанием отдельно проверяют готовность и наблюдение; автоматические тесты используют симуляцию.

## Единицы и границы

- Температуры API — градусы Цельсия; отображение на дисплее — целые значения. Измерения и расчёты регулятора сохраняют точность.
- Времена профиля — секунды; часы JavaScript и интервалы таймеров — миллисекунды. Не смешивайте относительные длительности участков с абсолютным временем развёрнутого плана.
- Ввод профиля целочисленный, повторы ограничены общей валидацией. UI-ограничения не заменяют серверную проверку.
- Подключение 230/380 В определяет политику нагрузок; обнаруженная версия платы не должна молча менять выбор модели.
- Калиброванная и исходная температуры доступны отдельно. Поправка не должна скрывать абсолютный перегрев исходной термопары.
- При открытии двери нагрев отключается, время профиля продолжает идти. При ручной паузе время замораживается. Закрытие двери не должно снимать ручную паузу.
- После завершения выдерживается вся последовательность итогового звука до следующего нагрева. После перезапуска активный профиль сам не возобновляется.

## Где живут данные

| Данные | Место и правила |
| --- | --- |
| Настройки запуска | Корневой `.env`; пример в `.env.example` |
| Модель, питание, переключатели, имя, операторский доступ | `config.json` в каталоге конфигурации пользователя |
| Библиотека профилей | SQLite рядом с конфигурацией |
| Калибровка | `temperature-calibration.json` рядом с конфигурацией; отдельные таблицы по модели, питанию и датчику |
| История, выборки, события и технические журналы | Только исправный смонтированный USB; нет резервной истории в RAM или на SD |
| Моточасы | USB; резервный снимок рядом с конфигурацией записывается один раз за загрузку ОС |
| Тема | Клиентский localStorage; независима от PIN-доступа |
| Права клиента | Серверная сессия конкретного клиента; введённый PIN в localStorage не сохраняется |

По умолчанию на Raspberry каталог конфигурации — `/home/pi/.config/mercury-v3`, программа — `/opt/mercury-v2/program`, USB — `/media/flash`. Пути могут переопределяться конфигурацией запуска. Обновляемый архив содержит программу, а не пользовательские данные.

Сбой USB отключает запись. Нельзя добавлять автоматический fallback на системный накопитель или буфер истории в памяти. Очистка при 80% заполнения удаляет только принадлежащие программе старые данные до целевых 50%; чужие файлы не трогает.

## Доступ и API

Основной HTTP — `8075`, совместимый мониторинг — `3457`; точные маршруты смотрите в `index.ts` и документах интеграции. Состояние мониторинга читается через `GET /status`, внешние команды — `POST /profile/start` и `/profile/stop` на порту мониторинга. JSON передаётся в теле запроса. Доступ интеграции проверяется при каждой команде.

Обычный и внутренний уровни доступа различаются. Не публикуйте внутренний код в клиентской сборке, подсказках и руководстве. Открытие прав на одном устройстве не открывает их другим клиентам. Передача профиля по согласованной политике не требует PIN, запуск — требует.

Маршруты калибровки: `GET /api/settings/calibration`, `POST /start`, `/save`, `/stop`, `/reset` с тем же префиксом. Сохранение проверяет датчик, конфигурацию, runId, завершённость и стабильность. Подробнее: [процедура и файл калибровки](calibration-2026-11-02.md).

## Изменения и проверки

При добавлении модели заведите отдельный JSON и проверьте отображение элементов, ламповые группы, ограничения нагрузки и характеристики нагрева/охлаждения. Измеренные характеристики одной конфигурации нельзя считать проверкой другой.

При добавлении команды укажите, разрешена ли она во время профиля, выключения и потери связи; проверьте доступ сервером. Нельзя ставить команды нагрева в очередь для отправки после восстановления сети.

Сборка и проверки из корня:

```powershell
pnpm typecheck
pnpm build
pnpm --filter @mercury/web build:pc
node --test apps/server/tests/*.test.mjs apps/web/tests/*.test.mjs packages/shared/tests/*.test.mjs
```

Серверные тесты импортируют `dist`, поэтому после изменения исходников сначала пересоберите проект. Они проверяют симуляцию и локальные HTTP-серверы; физических печей тестовый набор не нагревает. Аппаратные сценарии в `scripts` запускаются отдельно и могут действительно управлять печами.

`scripts/build-release.ps1` собирает обе web-компоновки, ARM64-пакет и проверяет его. Для упаковки нужен подготовленный `release/arm64-runtime.tar.gz`. В `release/publish` предназначены четыре файла: архив, `manifest.json`, `version`, `SHA256SUMS`. Установщик сохраняет конфигурацию, профили и калибровку вне дерева программы.

Руководство пользователя создаёт `scripts/build-user-manual.py` с ReportLab. После правки нужно отрисовать PDF и проверить страницы: успешная генерация не гарантирует правильную вёрстку.
