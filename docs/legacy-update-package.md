# Один пакет обновления для Raspberry

Сборка на ПК: `scripts/build-release.ps1` (или `pnpm build`, затем
`python scripts/build-universal-release.py`). Требуются Node 24, pnpm, Python
и локальный ARM64-кэш `release/arm64-runtime.tar.gz`. Кэш один раз получен
чтением зависимостей рабочей Debian 12 ARM64 Raspberry; Windows node_modules
в пакет не попадает. При изменении ARM64 runtime/native-зависимостей кэш
нужно обновлять соответствующей ARM64-сборкой.

Результат в `release/publish`:

- `3.0.1_linux-arm64-unpacked.tar.gz` — один универсальный архив программы;
- `version` — номер версии и MD5 для старого интерфейса;
- `manifest.json` — версия, имя архива и SHA-256 для нового интерфейса;
- `SHA256SUMS` — дополнительная контрольная сумма для ручной проверки.

В архиве нет config.json, базы профилей, выбранной модели и напряжения.
Модель и подключение выбираются в настройках при первом переходе.
Последующие обновления сохраняют настройки и профили в
`/home/pi/.config/mercury-v3`, вне заменяемой программы. Настройки одной печи
не переносятся на другую. После первой настройки поддержание выключено.
Профиль старого ПО импортируется с сохранением имени, точек и датчика.

## Файлы на сервере

Положить архив, `version` и `manifest.json` рядом в каталог обновлений.
Текущий URL по умолчанию: `https://www.nsc-com.com/soft/mercury`.
Если в старой конфигурации задан собственный HTTPS urlUpdate, launcher
сохраняет его при запуске. В программе v3 используется MERCURY_UPDATE_URL.
При новой публикации повысить version в корневом package.json и пересобрать:
новый интерфейс не устанавливает ту же или более старую версию.

Готовая сборка 3.0.1: сначала загрузить архив, затем заменить `manifest.json`
и `version`; `SHA256SUMS` можно положить рядом для ручной сверки.
Сервер публикации не изменяется автоматически при локальной сборке.
Сценарий `scripts/verify-release.py` сверяет SHA-256/MD5, содержимое программы,
ARM64 Node/Electron, границы путей и ссылок, отсутствие данных конкретной печи.
`scripts/build-release.ps1` выполняет эту проверку после упаковки.

Старый интерфейс проверяет version и MD5, распаковывает в /opt и запускает
`/opt/mercury-v2/mercury-soft-2`. Этот путь и пользовательская служба
mercury-v2 сохраняются в универсальном пакете; внутри запускаются API и
Electron v3 со встроенным Node 24 ARM64, без установки npm на печи.

Старый установщик удаляет содержимое /opt/mercury-v2 перед распаковкой
и перезагружает устройство. Обновление из старого интерфейса проводить
на остывшей печи без выполняемого профиля. Для 10.10.1.88 резервная копия
сохранена на ПК в `release/backups/mercury-v2-2.3.5-10.10.1.88.tar.gz`.

В новом интерфейсе кнопка «Обновить» находится в настройках. Она проверяет
манифест и загружает пакет; следующая кнопка устанавливает проверенный архив.
Во время профиля/поддержания обновление запрещено, перед установкой
проверяются выключенный нагрев и температура ниже 50 °C. Установка идёт
отдельным systemd-процессом, программа перезапускается; конфигурация и
профили сохраняются. SHA-256 перепроверяется перед распаковкой, пути архива
и ссылки ограничены каталогом пакета. Предыдущее приложение остаётся в
/opt/mercury-v2-before-*. При неудачном старте нового API установщик возвращает
прежнюю программу. Это механизм v3; старый установщик откат не выполняет.

## Проверено 19 октября 2026

64 автоматические проверки прошли; сервер, shared, panel и web собраны.
Vite сообщает о JS около 538 КБ. На 10.10.1.88 (Debian 12 ARM64) архив
распакован во временной папке без остановки старого ПО и без работы с реальной
платой. Проверены Node 24.21.0, системные и native-библиотеки, перенос старого
профиля, отсутствие заданной модели/напряжения, выбор 300/230 и 400/380,
сохранение конфигурации при повторной миграции. Установка поверх работающей
программы и нажатие кнопки обновления на реальной печи пока не выполнялись.
